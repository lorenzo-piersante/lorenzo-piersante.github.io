Five Minutes, One Pull Request: A Tiny AI Automation Experiment

Nov 27, 2026 AI, Automation, Programming 6 min read

The story I like to tell is that I went to bed with an empty branch and woke up to a pull request. Not a big one — a new tool page, a stylesheet, a script, and a card on an index — but it was mine, and I hadn't written any of it while awake.

The real version is less cinematic. The whole run took about five minutes on a quiet afternoon, and I was very much awake for it. I mention that up front because it is the most honest way to frame the experiment: this is not a story about an autonomous workforce. It is a story about one small issue, one short loop, and a result I was happy to merge.

This site is a small personal project: a handful of browser tools, a few notes, and whatever I happen to be tinkering with. I don't have a dramatic backlog. The issue tracker usually holds a couple of small ideas at most, which makes it a low-stakes place to try something like this.

The question was not whether an agent could replace a sprint. It was much narrower: can a coding agent take one small, well-specified issue and turn it into a change I would actually merge? The experiment needed three pieces: a way to read the queue, a loop to work through it, and a playbook so the result looked like it belonged on the site.

The engine

The first piece is a skill called github-issues. It is almost embarrassingly small: a Markdown file that tells the agent to run gh issue list and display the results in a readable format. That is the entire reader.

The second piece is bin/nightwatch.sh, a shell script that refuses to start on a dirty working tree, creates a timestamped branch, and runs the agent in a loop. 

#!/usr/bin/env bash

set -e

if [ -n "$(git status --porcelain)" ]; then
    echo "Working directory is dirty. Commit or stash changes first."
    exit 1
fi

ITERATIONS=${1:-10}
BRANCH="overnight-batch-$(date +%Y%m%d-%H%M%S)"

git checkout main
git pull origin main
git checkout -b "$BRANCH"

echo "Working on branch: $BRANCH"

for ((i=1; i<=ITERATIONS; i++)); do
    echo "=== Iteration $i of $ITERATIONS ==="

    opencode run --auto -m opencode/deepseek-v4.1-flash-free "$(cat <<'EOF'
1. Use the github-issues skill to fetch all open issues from this repository.
2. Run `git log main..HEAD --oneline` to see which issues were already handled on this branch. Commits use the format `ISSUE #<number>: <description>`.
3. Filter out every issue whose number already appears in that log.
4. If no issues remain after filtering, create `.nightwatch-complete` and exit.
5. From the remaining issues, choose ONE that seems most appropriate to work on next. You must ONLY CHOOSE ONE.
6. Implement the fix or feature for that issue.
7. Commit with message format: `ISSUE #<issue-number>: <short-description>` and in the body mark that it closes the related issue on GitHub.
EOF
)"

    git push -u origin "$BRANCH"

    # Check for completion
    if [ -f .nightwatch-complete ]; then
        echo "All issues complete after $i iterations."
        rm -f .nightwatch-complete
        echo "Review with: git log main..$BRANCH"
        exit 0
    fi
done

echo "Reached max iterations ($ITERATIONS). Review with: git log main..$BRANCH"

Two details matter more than the rest. First, the agent is told to pick exactly one issue per iteration. Not a batch, not a roadmap — one. That keeps each commit small enough to review in a couple of minutes, which is the only reason a short automated run is useful at all.

Second, the loop has no database. It runs git log main..HEAD --oneline and treats commit messages such as ISSUE #1: ... as the ledger of what is already done. The queue and the history are the same object. It is a little hacky, and it works surprisingly well.

There is also a stop condition: when no issues remain, the agent creates a marker file and the script exits. Crude, but enough for a personal project. The point was never to remove myself from the process — it was to move my attention from typing to reviewing, which is where I add more value anyway.

The playbook

The third piece is the one I am most pleased with. Before letting anything run unattended, I wrote a skill called new-tool. A skill is just a set of instructions the agent can load when a task matches, and this one describes, step by step, how a tool gets added to the site. 

---
name: new-tool
description: Creates a new tool page for this site. Use when asked to build, add, or develop a new tool. Creates tools/<slug>.html, adds any needed CSS/JS assets, and links the tool from tools.html.
---

# New Tool

Create a self-contained, responsive tool page and register it on the tools index.

[...]

- Reuse existing classes from `assets/css/style.css` before adding new ones.
- If the tool needs a few very specific styles, create `assets/css/<slug>.css` and link it after `style.css` (per `AGENTS.md`, do not bloat the main stylesheet).
- Put tool JavaScript in `assets/js/<slug>.js` (per `AGENTS.md`, do not inline scripts in new pages). Use `defer` and query elements by ID.
- Ensure it works on mobile: stack inputs, avoid fixed widths, test narrow viewports.

Without it, every generated page would invent its own layout, inline its own styles, and forget the navigation. With it, the output is boring — and boring is exactly what you want from an unattended process. Consistency is not a limitation here; it is the feature.

The morning after

A few minutes later, I had three commits and a merged pull request. The feature was a Lorem Ipsum generator: four sizes, random paragraphs truncated at sentence boundaries while always keeping at least two sentences, and a copy-to-clipboard button. The agent had created the page, added a dedicated stylesheet, put the JavaScript in assets/js/, and linked the card under "Software" in tools.html. The diff looked like something I would have written on a good day.

What surprised me was not that the code worked. It was that the structure matched. The skill had turned a vague request into a checklist, and the checklist had survived contact with an autonomous loop. The agent did not just produce a page; it produced the page this site would have asked for.

What actually worked

  • Small scope. One issue per iteration meant one focused change per commit. There was never a fifty-file diff to untangle in the morning.
  • An explicit stop condition. The run knew when it was finished, so it did not keep inventing work to stay busy.
  • Reusable instructions. The skill is the difference between a one-off demo and a repeatable process. Writing it took less time than reviewing a messy generated page would have.
  • Reviewable output. One branch per batch, one feature per commit, and a pull request at the end. The human review step never disappeared.

What this is not

I want to be honest about the limits, because the interesting part of this experiment is also the part that keeps it small.

  • No tests and no CI. The generated tool is checked by opening it in a browser, not by a test suite.
  • No concurrency control. Two runs at the same time would collide on the same branch and the same issues.
  • No cost tracking. I did not measure tokens, time, or money. For a personal project with a handful of issues, that felt acceptable; for anything larger, it would not be.
  • No automatic merge. A human still reads the diff and decides. That is deliberate.
  • A few rough edges. The clipboard API needs a secure context, the shell loop can stop early if a push fails, and the marker file is a very simple way to communicate "done".

None of these are surprising. They are the normal gaps between a fun experiment and a system you would trust with anything important.

Closing thoughts

So, what is this? It is a very basic experiment for a personal project. There is no orchestration platform, no dashboard, and no clever scheduler — just a shell script, two Markdown files, and an issue tracker doing double duty as a queue. I am not claiming it replaces anything or that it is ready for a team.

But that is exactly why I like it. The barrier to trying an idea like this is now almost zero: a branch, a loop, and a few sentences of instructions. The result was a small, useful feature that I would otherwise have put off for another weekend. If the worst thing that happens is that I review a slightly odd diff over coffee, that is a pretty good trade.

I am looking forward to the next five-minute experiment.
